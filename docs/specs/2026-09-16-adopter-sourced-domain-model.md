# Adopter-sourced domain model

Design for removing one SaaS's domain model from the platform's artifacts and
sourcing it from the adopting SaaS's own git repository instead. The decision
and its reasoning are [ADR-013](../adr/0013-the-domain-model-is-adopter-data-not-a-platform-artifact.md);
this document specifies the work.

## Current state

Two authored inputs describe the adopter's domain, and both are compiled into
platform artifacts:

| Input | Where it lives today | How it reaches a running service |
|---|---|---|
| Resource manifest (156 FHIR resources) | `libs/cataloggen/manifest.yaml`, `//go:embed`ed into the package | Generates policies, schemas, tests and the DB seed at build time; the policy tree ships in `cerbos-poc/cerbos-assets` |
| Capability catalog (400 capabilities) | `deploy/cerbos/catalog/ui-capabilities/*.yaml` | `COPY`d into `cerbos-poc/cerbos-assets`, then an initContainer copies it into an `emptyDir` the ADS and Administration Service mount |

Everything else derived from the manifest - `deploy/cerbos/policies/**`,
`deploy/cerbos/catalog/resources/**`, `deploy/liquibase/changelog/data/*.csv`
and the §19.1 test suite - is generated output, regenerated by
`make catalog-gen` and `make capability-gen` and drift-checked in CI by
`make catalog-check`, `make capability-check` and `tests/architecture`.

## Target state

The adopter's repositories hold only authored content. ADR-014 splits them in
two, with independent refs:

```
<adopter-resource-repo>/<subdir>/
└── manifest.yaml              the resource model

<adopter-capability-repo>/<subdir>/
└── ui-capabilities/
    ├── <module>.yaml          one file per module
    └── ...
```

Each is configured with repository URL, ref, subdirectory, credentials and
poll interval, and each is cloned and pinned by resolved commit SHA. Because
a capability leaf must resolve against the resource catalog (§12.2) while
nothing about a resource refers to a capability, activation is asymmetric:
a capability sync validates against the active resource catalog, and a
resource sync is refused if it would orphan an active leaf. See ADR-014.

A syncer pulls each ref, validates it,
generates the policy tree, schemas and test suite, compiles the whole tree,
runs the precedence matrix over a bounded sample (ADR-015), and only then
installs: the policy tree onto the directory
Cerbos watches (`atomicInstall` + `ReloadStore`, as `libs/policyrelease` does
today) and the capability catalog onto the volume the ADS reads. A sync that
fails any gate leaves the previous content serving.

The platform's own images contain no resource or capability content.

## Slices

Each slice is independently shippable and independently valuable. They are
ordered by dependency, and slice 1 is the only one specified in full here;
the others get their own specs when reached.

1. **`cataloggen` reads its manifest from a path** - removes the `embed`, the
   single change that stops the platform binary from containing a domain
   model. Specified below. **Delivered.**
2. **Capability catalog authored per module, with a pre-decoded artifact** -
   splits `generated.yaml` into one file per module and teaches `FSCatalog` to
   prefer a pre-decoded artifact, removing the measured OOMKill at ~60,000
   capabilities. Independent of git sourcing: worth doing whether or not the
   content later moves.
3. **Git syncer** - generalises the `policy-release` component from a
   Gitea-tag poller into an adopter-repository syncer, and promotes it from
   `dev-chaos` to every installation.
4. **Sync-time verification gate** - splits the §19.1 guarantee per ADR-015:
   a generator property test in CI, and a bounded activation gate so a
   manifest CI never sees is still checked before it serves.
5. **Governance** - audit and approval for domain-model changes, which become
   a privileged runtime operation.

## Slice 1: `cataloggen` reads its manifest from a path

Delivered. `LoadManifestFile` and `DefaultManifestPath` replace
`LoadEmbeddedManifest`, both generators take `-manifest`, and
`tests/architecture/manifestembed.go` is the invariant that stops the
directive coming back. The manifest stays committed here as the example
domain model, as this slice intended; moving it out is slice 3's job.

### Why this is small

The seam already exists. `ParseManifest(raw []byte) (*Manifest, error)` is
already documented as parsing "from an arbitrary source", performs all
validation and key derivation, and is already used directly by tests with
fixture manifests. `LoadEmbeddedManifest` is a four-line wrapper that reads
`manifest.yaml` out of the embedded FS and calls it.

There are four callers outside `libs/cataloggen`'s own unit tests, and every
one of them is a generator entry point or a drift test - no service calls it:

- `libs/cataloggen/cmd/cataloggen/main.go:28`
- `libs/capabilitycatalog/cmd/capabilitycatalog-gen/main.go:41`
- `tests/architecture/catalogdrift_test.go:22`
- `tests/architecture/capabilitydrift_test.go:28`

### The change

Add `LoadManifestFile(path string) (*Manifest, error)`, a sibling of
`LoadEmbeddedManifest` that reads from the filesystem and delegates to
`ParseManifest`. Both generators gain a `-manifest` flag. The flag defaults
to `<root>/libs/cataloggen/manifest.yaml`, so `make catalog-gen`,
`make catalog-check`, `make capability-gen` and `make capability-check`
continue to work unchanged and the committed FHIR catalog keeps regenerating
byte-identically.

`LoadEmbeddedManifest` and the `//go:embed` directive are then deleted, and
the architecture tests read the same default path. Nothing keeps a manifest
inside the binary.

The manifest stays committed at `libs/cataloggen/manifest.yaml` after this
slice. It becomes the *example* domain model this repository happens to
generate from and the fixture the test suites use - not a compiled-in
default. Moving it out of this repository entirely is slice 3's job, once
something exists to source it from.

### What must not change

- Every file under `deploy/cerbos/policies/**`,
  `deploy/cerbos/catalog/resources/**` and
  `deploy/liquibase/changelog/data/*.csv` regenerates byte-identically. The
  existing golden-file tests in `libs/cataloggen` and the drift checks in
  `tests/architecture` are the proof, and they must pass unmodified except
  for the manifest-loading line.
- `make catalog-check` and `make capability-check` keep failing on drift, and
  keep needing no argument.
- No service gains a manifest dependency. `libs/loadmodel` and
  `libs/capabilitycatalog` consume a `*Manifest` they are given; they do not
  learn where it came from.

### Testing

- A unit test that `LoadManifestFile` on the committed manifest produces a
  `*Manifest` deep-equal to what `ParseManifest` produces from the same bytes
  read directly, so the new path adds no transformation.
- A unit test that a missing or malformed path fails with an error naming the
  path, rather than falling back to anything.
- An architecture test asserting no `embed` directive remains in
  `libs/cataloggen`, in the style of the existing four invariants, each of
  which has a deliberate-violation test.
- The existing golden and drift suites, unchanged, as the regression proof.

### Acceptance criteria

1. `grep -r "go:embed" libs/cataloggen` returns nothing.
2. `make catalog-gen && git diff --exit-code` is clean.
3. `make capability-gen && git diff --exit-code` is clean.
4. `make catalog-check`, `make capability-check` and `make arch-test` pass.
5. Both generators accept `-manifest <path>` and generate from a manifest
   outside this repository when given one.

## Open questions

All four are now resolved, in [ADR-014](../adr/0014-adopter-content-is-two-repositories-cloned-and-pinned-by-commit-sha.md)
and [ADR-015](../adr/0015-the-exhaustive-policy-matrix-proves-the-generator-not-the-domain-model.md).
They are kept here with their answers so the reasoning that unblocked slices
3-5 is readable beside the question that prompted it.

- **Where does the §19.1 guarantee move to?** *Resolved (ADR-015): it splits.*
  Two generated test suites are byte-identical once the resource name is
  normalised away, so the 11,303 assertions are one generator-correctness
  proof replicated 156 times. Generator correctness moves to a property test
  over synthesised manifests in CI; the sync-time gate becomes manifest
  validation, `cerbos compile` over the whole tree, and the precedence matrix
  over a bounded sample - O(1) in the adopter's resource count.
- **One repository or two?** *Resolved (ADR-014): two, with independent refs.*
  The §12.2 referential integrity this creates is handled by an asymmetric
  activation rule rather than a validated pair of SHAs - resources lead,
  capabilities follow, and a resource sync is refused if it would orphan an
  active leaf.
- **What is the unit of an installation?** *Resolved (ADR-014): installation-wide,
  deferred.* Nothing in the schema carries application identity, so the
  dimension is far larger than sourcing content. The per-repository
  `subdirectory` setting keeps it reachable later.
- **Does the syncer keep using the Gitea API, or clone?** *Resolved (ADR-014):
  clone a ref and pin the resolved commit SHA.* A SHA gives the immutability
  `SelectTag`'s protected-tag rule was protecting, on any host. What is lost
  is the authorization control on minting a release tag, which this platform
  never had for this path (DEVIATIONS N3) and which slice 5 must supply.
